# ADR 0009：AI 工作室使用 MySQL 任务队列与月度预算

- 状态：已接受（由 ADR 0014 扩展：AI 流程改为“角色 + 技能”在同一队列上运行）
- 日期：2026-10-21
- 依据：2026-10-21 设计变更（用户已批准，见 [v1.0 变更记录](../06-releases/v1.0/changes.md)）

## 背景
伙伴形象、呀哈哈款式、规则解析、课程生成都要调用外部 AI 或本机进程（Piper、资料解析），耗时从秒到分钟不等，且有费用。服务器只有 2 GB 内存，不宜引入 Redis 或独立队列服务。

## 决策
- 任务表 `ai_jobs` 作为队列：执行器在 API 进程内每 2 秒轮询，按 `queued_at` 顺序抢占空闲槽位；`running_slot` 1/2 唯一保证全站最多 2 个运行中任务，生成列 `local_slot` 唯一保证本机进程类任务同时最多 1 个；运行中每 15 秒心跳，超过 2 分钟无心跳视为中断，最多重试 3 次。
- 生成前先显示**预估费用**，管理员确认后才入队；`ai_budget_months` 在同一事务预留预估费用，CHECK 保证“预留 + 已花费 ≤ 月度上限”（已实测），任务结束按实际费用结算（实际 ≤ 预估）。
- 所有 AI 产物先是草稿，经管理员审核才对孩子可见；提示词由服务器模板拼装，资料文本只作为数据段传入并做提示注入防护。

## 后果
无新增中间件；预算与并发由数据库约束兜底；吞吐量有限（适合单个管理员的工作量）。

## 未采用的方案
Redis/BullMQ（额外内存与运维）；无预算上限的直接调用（费用不可控）。
