# ADR 0016：保留单元层（课程 > 单元 > 关卡）

- 状态：已接受（修订 ADR 0008 的进度键与内容层级）
- 日期：2026-10-21
- 依据：2026-10-21 用户决定（见 [v1.0 变更记录](../06-releases/v1.0/changes.md)）

## 背景
ADR 0008 的内容层级是“年级 > 课程 > 版本 > 关卡 > 题目”，示例课程 ID 形如 `en-g1-u03`，即一个“课程”实际上只是教材的一个单元。这样一册书会被拆成十几门互不相关的课程：开放、排序、版本与 AI 生成都要逐个处理，孩子端也看不到“一册书里的第几单元”。用户决定在课程与关卡之间保留**单元**层。

## 决策
1. **层级**：年级 > 课程 > 单元 > 关卡 > 题目。**课程** = 一册（如一年级上册，`en-g1-a`；下册 `en-g1-b`）。**单元** = 围绕一个主题的一组关卡（如 Unit 3 Animals），每单元 3–6 关。
2. **版本以整门课程为单位**：发布、审核、回滚都针对整门课程；课程版本不可修改，并包含它的全部单元。新表 `units`（随版本只追加，应用账号只有 SELECT、INSERT）；`levels.unit_id` 通过复合外键 `(course_version_id, unit_id)` 保证关卡与单元属于同一版本。
3. **稳定键**：单元有跨版本稳定的 `unit_key`（如 `u03`，在版本内唯一）；`level_key` 改为**在单元内唯一**。进度键由 ADR 0008 的 `(course_id, level_key)` 改为 `(course_id, unit_key, level_key)`。单元改名（换 `unit_key`）或关卡跨单元移动视为新的单元/关卡，进度不迁移（开放问题 Q28）。
4. **解锁**：单元在课程内顺序解锁，关卡在单元内顺序解锁；第 N+1 单元的第 1 关在第 N 单元最后一关通过后解锁。新表 `unit_progress` 记录每个孩子每个单元的计数，以及只写一次的 `first_completed_at`（解锁下一单元，不会因新版本加关卡而撤销）与 `first_all_three_star_at`（“单元首次全 3 星级通关”触发只发生一次）。
5. **家长开放**仍按年级/课程，不按单元。
6. **呀哈哈发现**：课程规则的范围改为 `spec.scope.targets = [{courseId, unitKey?, levelKey?}]`（1–20 个，可指向课程、单元或关卡）；数据库用 `JSON_SCHEMA_VALID` 检查结构，并检查“单元首次全 3 星级”不能指向关卡、“指定关卡通关”的目标必须都是关卡；目标是否存在由服务端校验。
7. **AI 工作室**：一次生成整门课程或一个单元（加入现有草稿）；模板描述一个单元的关卡结构（`levelsPerUnit`、`unitPlan`）；费用按单元预估。
8. **单元大小**是系统设置 `content.unit_levels`（默认 `{min:3, max:6}`，数据库 CHECK 1 ≤ min ≤ max ≤ 12，已默认，可调整，开放问题 Q26），由自动检查 K13 执行，不是数据库硬约束。
9. 报告增加 `daily_reports.units_completed` 与按单元的进度。

## 后果
- 表数 65 → 67（`units`、`unit_progress`）；`0001_init.sql` 尚未部署，直接修订；在临时 MySQL 8.4.6 上重新验证 236/236（历史；2026-10-30 起引擎为 PostgreSQL 16，见 ADR 0023）（[数据模型附录 A](../03-design/data-model.md#附录-a-数据库验证结果)）。
- 一册书的开放、排序、发布只需处理一门课程；单元级 AI 生成让预算与失败重跑的粒度更小。
- 发布事务多写一张表；单元的增删与排序需要后台表单与接口；排期不变（单元编辑并入 W7–8 课程编辑）。

## 未采用的方案
- **单元单独版本化**（每个单元一门“课程”）：一册书难以整体开放与发布，跨单元解锁要跨课程判断。
- **单元只做关卡上的分组标签**（不建表）：无法给单元稳定键、标题与封面，也无法用外键保证同一版本。
